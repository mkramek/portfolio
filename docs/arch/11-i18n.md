# Internationalization

Route-based i18n across the public portfolio, the admin panel, the generated CV, and the JSON export/import — English default, additional locales configured from the admin panel itself, no i18n runtime shipped to the browser.

## Two string populations

Everything user-facing splits into two kinds, translated by two different mechanisms:

- **UI chrome** — button labels, tab headers, field labels, the CV document's section headings. Fixed at deploy time, shipped as TypeScript dictionaries (`lib/i18n/dictionaries/<locale>/{public,admin,cv}.ts`).
- **Owner content** — profile, roles, projects, section labels, the tailored CV summary. Editable at runtime, stored per-locale in the `Translation` sidecar table (see [[adr/013-sidecar-translation-table|ADR-013]]) and managed from the admin panel's Translations tab.

Confusing the two would be a mistake: chrome is complete-by-construction (a missing dictionary key is a build error, see below), content is expected to be partially translated at any given time and falls back to English field-by-field.

## Route shape

Every route — public and admin — lives under a `[lang]` root segment: `app/app/[lang]/{layout,page,coming-soon}.tsx` and the entire `app/app/[lang]/admin/**` tree. `/api/**` route handlers are **not** locale-prefixed; they're the same API surface regardless of which locale the caller is browsing in. See [[adr/012-locale-prefixed-routing|ADR-012]] for why every locale (including English) gets a URL prefix — `/` always 308-redirects to `/en`.

`[lang]` sitting above the root layout makes it a Next.js **root parameter**: `import { lang } from "next/root-params"` gives any Server Component or server-side utility the current locale with no prop drilling, including deep inside `lib/`. Its constraints shape the rest of the design:

- Works in Server Components and server-side utilities. **Not** in Route Handlers, Server Actions, or Client Components.
- Route Handlers (everything under `app/app/api/**`) take locale explicitly, from the request body or a query param, when they need it at all (most don't — the CV PDF route is the one exception, see below).
- Client Components receive already-resolved strings as props. A client component that needs to build a locale-prefixed `href` (nav links, `router.push` targets) recovers the locale from the URL itself via `lib/i18n/use-locale.ts`'s `useLocale()` hook (reads the first path segment), since it can't import `next/root-params`.

`app/proxy.ts` (Next's middleware) does two independent jobs: redirect any path missing a valid locale prefix to `/${DEFAULT_LOCALE}${path}`, and — after stripping a valid prefix — apply the pre-existing `/admin/**` auth gate to what remains. A path like `/admin/foo` (no locale) safely round-trips through the redirect branch to `/en/admin/foo` before the auth check ever runs, so a missed `href` update anywhere in the app degrades to one extra redirect, not a broken link or an open gate.

## Locale catalogue vs. enabled locales

Two different questions, two different answers:

- **Which locales does this app ship a dictionary for at all?** `LOCALE_CATALOGUE` in `lib/i18n/config.ts` — an in-code constant (`en`, `pl` today). Adding a locale means adding dictionary files and a catalogue entry; it is not admin-configurable, because there's no UI text to fall back to for a locale with no dictionary.
- **Which catalogue locales are actually turned on for visitors right now?** The `Locale` DB table (`code`, `enabled`, `sortOrder`), read via `getLocales()` in `lib/content.ts` — merge-on-read against `LOCALE_CATALOGUE`, same pattern as `Theme`/`Section` (ADR-007): no row means "not yet touched," not "doesn't exist." `en` is always enabled and never needs — or gets — a row proving it; every other catalogue entry defaults to disabled until the admin's Locales tab (`/admin/locales`) first toggles it.

`app/[lang]/layout.tsx` only validates catalogue membership (`isLocaleCode`) — a garbage segment like `/xx` 404s regardless of the enabled set. `app/[lang]/page.tsx` additionally checks *enabled* for non-default locales, so a disabled-but-cataloged locale 404s on the public site while staying fully reachable under `/admin/**` — disabling the locale you happen to be editing in must never lock you out of the panel.

The proxy can't reach the database at all (no Prisma import in `proxy.ts`), so its redirect logic only ever consults the in-code catalogue, never the enabled set. This is intentional and harmless: an admin visiting a cataloged-but-disabled locale's public URL still gets a proper 404 from `page.tsx`, just one redirect-free hop later than if the proxy also knew about it.

## Owner content: the `Translation` sidecar

```
Translation { entity, entityId, locale, values: Json, updatedAt }
@@id([entity, entityId, locale])
```

- **Which fields are translatable per entity** is declared once, in `lib/i18n/translatable.ts`, as `FieldSpec[]` — the same shape the admin CRUD forms already render fields from (`lib/admin/fields.ts`), so the Translations tab reuses `field-control.tsx` unmodified. Proper nouns are excluded (company names, product names, people's names, specific skill tags); free-text dates like `Role.end` (`"Present"`) are included.
- **The merge** (`lib/i18n/localize.ts`'s `localize()`/`localizeFrom()`) is field-level: a translation's `values` overrides the English base one declared field at a time, and a blank or absent value for a given field falls back to that field's English text — never to a blank page. `values` is stored **nested**, mirroring the base entity's own shape (`{ caseStudy: { context: "…" } }`, not a flattened `"caseStudy.context"` key), so `getPath`/`setPath` (`lib/admin/fields.ts`) walk both consistently.
- **Reading a locale** for the public portfolio (`lib/i18n/content.ts`'s `getLocalizedContent()`) or the CV (`lib/cv.ts`'s `resolveLiveCv()`) costs exactly one extra query — `Translation.findMany({ where: { locale } })` — beyond what the English-only read path already did, merged in memory against the base rows.
- **Completeness** (`lib/i18n/completeness.ts` + `lib/i18n/report.ts`) only counts a field as "needing" translation when its English base is non-empty — an empty field isn't a missing translation, it's just empty. `getTranslatableInventory()` in `report.ts` is the single source of "every translatable row in the database," used by both the Locales tab's per-language percentage badge and the Translations tab's completeness column.
- **Cascade delete**: removing a role/project/etc. must explicitly delete its `Translation` rows (no DB-level FK — see ADR-013's consequences). `lib/admin/routes.ts`'s generic `itemRoutes` factory takes a `deleteTranslations(entityId)` callback per entity, called before the row itself is deleted.

## Admin chrome: dictionaries

`lib/i18n/dictionaries/<locale>/{public,admin,cv}.ts`, loaded via `lib/i18n/dictionary-loader.ts`'s `loadDictionary(locale, namespace)` — a plain, locale-explicit function, dynamically `import()`ing only the requested namespace so a page that only needs the public dictionary never pulls the (much larger) admin one into its server module graph. `lib/i18n/dictionaries.ts` wraps it with the `next/root-params`-based `getPublicDictionary()` / `getAdminDictionary()` / `getCvDictionary(locale)` used by pages — kept in a separate module from the loader specifically so the loader stays testable with a plain locale argument, no request context required (`next/root-params` throws if imported outside one).

Each `en/*.ts` file is the **source of truth**, typed against a hand-written interface (not `typeof en` derived from an `as const` literal — that would infer every leaf as its literal English string, rejecting any other language's text as "not assignable"). Every other locale's file is typed `satisfies <Namespace>Dictionary`, so a missing or misspelled key is a **build error**, not a silent English fallback — admin chrome can never end up half-translated the way owner content can.

The one deliberate exception: `AdminDictionary.fields`, a flat `Record<string, FieldOverride>` keyed `"<entity>.<fieldKey>"` (e.g. `"role.company"`), consumed by `lib/admin/fields.ts`'s `localizeFieldSpecs()`. It's typed as an open record on purpose — a locale missing one override just keeps that field's English label rather than failing the build, since it's additive sugar over the structural `FieldSpec[]` arrays (`ROLE_FIELDS`, `PROFILE_FIELDS`, …), not a second source of truth that must track every field 1:1.

`localizeListConfig()` (also in `lib/admin/fields.ts`) builds a full locale-specific `ListConfig` (title, help, column labels, and — for `roles` specifically — the dense table view's `DETAIL` column translated through the same depth-option map the field editor uses) from the dictionary's `lists`/`fields` maps, so a list page (`/admin/experience`, `/admin/projects`, …) resolves everything server-side and hands the client component (`EntityView`) plain, already-localized data.

## CV locale — independent of the admin's browsing locale

`CvSettings.locale` / `CvSnapshot.locale` are a **separate** axis from the `[lang]` the admin happens to be browsing the builder in — set from a language dropdown in the CV builder (`components/admin/cv-builder.tsx`), defaulting to English. `lib/cv.ts`'s `resolveLiveCv(locale)` merges translations exactly like the portfolio's read path; `components/cv/cv-document.tsx`'s printed section headings ("Work Experience", …) come from `getCvDictionary(cv.locale)`, not the URL. A `CvSnapshot` freezes its content locale at generation time alongside the resolved text, so redownloading an old snapshot stays faithful even if `CvSettings.locale` has since changed.

`/api/cv/pdf`'s headless-Chromium navigation always targets `/${DEFAULT_LOCALE}/admin/cv/print` — the `[lang]` segment there only satisfies the route's structural requirement (screen-only chrome, hidden in print) and has no bearing on the document's actual text, which is driven entirely by `cv.locale`/`snapshot.locale`.

## SEO

- `app/[lang]/layout.tsx`'s `generateMetadata` sets `metadataBase`, a localized `title`/`description` (from `getLocalizedContent(locale).profile`), `alternates.canonical`, `alternates.languages` for every enabled locale plus `x-default → /${DEFAULT_LOCALE}`, and `openGraph.locale`/`alternateLocale`. The pre-publish "coming soon" state gets equally content-free metadata (fixed dictionary copy, `robots: { index: false }`) — no `Profile.name` leak, matching [[04-setup-publish-gate]]'s "no personalization before publish" rule.
- `app/sitemap.ts` returns one entry per enabled locale, each carrying `alternates.languages` for every other enabled locale (native `MetadataRoute.Sitemap` support) — empty while the publish gate is closed. `app/robots.ts` disallows `/*/admin` and `/api/`.
- A `Person` JSON-LD graph (`lib/seo.ts`'s `personJsonLd()`) is emitted on the public portfolio, built entirely from data `getLocalizedContent()` already fetched — no extra query — and only once setup is complete.
- The language switcher (`components/portfolio/language-switcher.tsx`) is plain `<a href="/pl">` anchors — no client component, no JS, no cookie — rendering only enabled locales, nothing at all when there's just one.

## Caching

See [[adr/014-isr-for-public-portfolio|ADR-014]] for the full reasoning. In short: the public route dropped `force-dynamic` in favor of classic ISR (`revalidate = 300` on the shared root layout), with `lib/revalidate.ts`'s `revalidatePublicPortfolio()` called from every admin write that could change public output (content, sections, theme, locale enablement, a translation) so edits still show up immediately despite the cache — preserving ADR-006's "no draft/publish workflow, edits go live" guarantee. Admin routes are unaffected: a `force-dynamic` child route forces the whole request dynamic regardless of what the shared ancestor layout declares.

Neither `app/[lang]/layout.tsx` nor `page.tsx` declares `generateStaticParams` — doing so would make `next build` attempt to prerender `/en`/`/pl` at build time, which needs a reachable database the Docker/CI build doesn't have. Both locales render on-demand on first visit instead (`dynamicParams` defaults to `true`) and are cached from then on.

## Export / import

`exportAll()`/`importAll()` (`lib/data.ts`) include `translations` (every row, unfiltered) and `locales` (the effective, defaults-merged list — same convention as `theme`/`sections`, see [[02-data-model|Data Model]]). `exportSchema` (`lib/schemas/export.ts`) declares both `.default([])`, so a backup taken before i18n shipped still imports unchanged.

## Terminology note

`Language` was already taken in this codebase — `model Language { name, level }` is spoken-language proficiency shown on the CV, unrelated to UI/content locale. The i18n concept introduced here is named **Locale** throughout (model, admin tab, schemas, dictionaries) specifically to avoid colliding with it.
